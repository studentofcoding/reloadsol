The standard we already have — twice, and disagreeing

The canonical feature spine is real and it is applied: ~82,800 of 82,861 outcome rows carry it, because insertStrategyOutcome canonicalizes on every write. The problem is what sits beside it. Measured on prod: 113 distinct top-level keys over 2.65M key instances, one domain carrying 101 of them — and domain_features holding a near-complete second copy of the same fields, with no rule naming which copy wins.

One row, two copies — the double-booked blob

That is the whole problem in one picture. It is not that we lack a standard — it is that the standard is duplicated inside every row, and on ~3% of rows the duplicate disagrees with the original. Any consumer reading one copy and not the other is silently wrong on those rows.

The target — four layers, and what must land first

What it costs — census, blast radius, order

CENSUS (PROD, 2026-10-01)

113 keys, per-domain shape

  • 113 distinct top-level keys · 2.65M key instances · 112 MB (avg 1,418 B/row).
  • mcap_tracker alone carries 101 of the 113; signals 66; trending_bot 59 (on 77,431 rows); gmgn/social 49; dlmm 31.
  • The blob is shaped per domain, not shared — so a single flat schema has to reconcile six shapes.

BLAST RADIUS

11 writers, 4 schemas, 3 models

  • 11 write sites — incl. the one script that bypasses the choke point (replay-mcap-first-seen-14d).
  • Schema defined 4×: TS entry, TS closed-loop (a different 13-col set), Python features.py, Python pattern_features.py.
  • Key names hardcoded in every TS reader + Python exporter + UI; the pattern meta already drifts (7 cols on disk vs 10 in code).
  • Retrain triggers: v2-gate, v2-potential, pattern-gate, closed-loop.

ORDER

Registry before rename

  • P1 registry + version check → P2 one builder → P3 alias reads → P4 history → P5 backfill → P6 retrain.
  • Landing a rename before the retrain makes the gate read renamed features as missing — zero-filled, no error.
  • Status: both SPECs written, docs-only. No code changed, nothing committed.
