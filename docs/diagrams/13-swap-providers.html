Routing · swap providers, measured on prod

The transaction was never the expensive part

Four providers, benchmarked from inside reloadsol-web on flowey-vps — the same egress and the same JUPITER_API_KEY production uses. Taker was the live wallet 3V3N5xh…; mints came from trading_records (12-day window) plus SOL/USDC/BONK at ~$50 notional. Read-only throughout: /order, /quote, /swap (build) and /quote-and-swap were called; nothing was signed and nothing was broadcast. Every lane was measured through to an unsigned transaction, and every returned transaction was decoded to confirm it is signable — 19 of 19 came back v0 with a single signature and the taker as fee payer.

The verdict

One lane. /swap/v2/order?taker= → simulate → sign → /swap/v2/execute → verify on-chain. Do not fan out, do not switch lanes per direction, and do not route on price.

Why that lane and no other. It is the only one that simulates before it returns — so it refuses a swap the wallet cannot pay for, and refuses the transfer-fee and stale-route cases that Lite and Raptor hand back as transactions that can never land. It is also the only lane whose transaction something can finish: /execute needs the requestId that only /order issues. Measured end to end: 3/3 landed, ~888 ms, against 1,732–5,084 ms for a Lite tx pushed through our own RPC. Its ~220 ms prepare is the price of that simulation, not waste.

Reject outright: the parallel best-of fan-out (measured +5 bps mean / 0 median for 2.59× the swap); Raptor as an execution path (0/4 signatures for transactions that never reached the chain); Lite as an execution path (per-IP ban outlasting ten minutes, no key can raise it, no simulation, and Jupiter cannot finish it); DFlow (worst price, v1 tx un-signable); swap.io inline (no build endpoint, slowest lane); Titan (needs a key).

Where the value actually is. Not in routing — that is a ~5 bps question. It is in the two correctness holes: an unlandable-transaction class that nothing in our model can see (DEW's 1 % Token-2022 transfer fee silently consumed the whole 100 bps slippage budget), and a provider that reports a signature for a transaction it never broadcast. Then an explicit priority fee, and confirming on the chain rather than from a response body. Lite stays for estimates. Raptor stays for quoting — it is genuinely good there (294/294 at 5 rps, p50 199 ms) — and never for sending.

And the batch is a budget problem, not a lane problem. It is N tokens × 2 keyed calls at 0.5 rps, so the gate — not latency — sets the wall time: at the measured ~2 s per token, five tokens cannot finish in under ten seconds however fast any one call is. Raptor's docs claim no rate limits and that held — 20 concurrent builds in 641 ms, zero rejections — but its transactions carry no requestId, so nothing can land them but our own RPC, and with no simulation behind them. The real bulk lever is the Jupiter quota, not the router.

The 200 ms is simulation

  • Jupiter's Lite lane reaches an unsigned tx in ~39 ms across two calls — 5× faster than a single /order.
  • So the ~200 ms /order costs is not building the transaction. It is the pre-flight simulation it runs.

No single provider wins

  • Raptor beats Jupiter by +1.31 % selling DEW→USDC and loses by −2.41 % on DEW→BPX.
  • Fired together, the best source changes pair by pair — which is the entire case for a best-of pick.

200 OK is not success

  • /order answers 200 with an empty transaction and "Insufficient funds" when the wallet is short.
  • The Lite /swap build does not pre-check — it returns a tx the wallet cannot afford.

The optimal scenario — and the Step-0 correction that killed it

This page's own recommendation was tested on the server before any code was written, and it failed. /order alone measured 226 ms and the fan-out 585 ms — 2.59×, not the "same wall time" argued below. The cause is in the same run: Raptor's leg is not the ~191 ms the isolated five-pair loop showed. On fresh mints it measured p50 528 ms, range 189–656 ms, against Jupiter's 226 ms — and a fan-out inherits its slowest leg. The price edge does not survive a random sample either: across 40 real traded mints the best-of gain over Jupiter-only was +5 bps mean, 0 median, with Raptor losing by as much as −350 bps where it did lose — not the +55 / +131 bps these five hand-picked pairs implied. So the fan-out and the hops escalation are cancelled; the desk path stays sequential. What survives from the analysis below is the shared condition set (for the affordability abort) and the continuous oracle — the instrument that would have caught this sampling error.

Recorded below is the proposal as it stood, kept because the reasoning error is the instructive part: it generalised from five pairs that were not a sample of our book. Today's desk path still calls /order and reaches for Lite only when it fails; swap-quote-parallel.ts is sequential and short-circuits, and its own comment says "Raptor is not queried".

Two things the real run taught us that no quote benchmark could

  • DEW carries a 1 % Token-2022 transfer fee, and it eats the entire default slippage budget. The mint has a transferFeeConfig of 100 basis points. At slippageBps=100 the transfer fee consumes the whole tolerance, so the router's own post-check fails with 6001 SlippageToleranceExceeded — the transaction builds in 21 ms and can never land. Raising slippage to 300/500/1000 makes the identical route simulate cleanly. This is a token-class bug, not a lane bug, and it would hit any transfer-fee mint.
  • Only /order would have caught it before we sent anything. Fake the same swap across all three lanes and simulate: Lite and Raptor hand back a transaction that fails simulation, while /order refuses server-side and never returns an unlandable tx. That is the ~200 ms the expensive lane charges for, and it is worth it.
  • Without a priority fee, the transaction simply never lands. The first live attempt was broadcast and never appeared on-chain (getSignatureStatuses → null, balances unchanged, no double-spend). With 150,000 lamports it landed in both directions.
  • And the route changes between attempts on the same pair. The same DEW sell produced Manifest, then Meteora DLMM + Kipseli; the buy produced Deriverse + TesseraV + Meteora DLMM, then Manifest. A quote is not a stable description of the execution path.

Lite's rate ceiling — probed, not guessed

lite-api.jup.ag keyless · our VPS IP · 2026-10-01

So "the highest TPS before 429" has no clean answer: the limiter is not a rate you can tune to. It absorbs a surprisingly large burst — 32 concurrent or ~75 rps — and then locks the IP out for about two minutes during which even a trickle is refused. That is the shape that matters operationally: a burst succeeds, then everything behind it fails for two minutes. Ours is a keyless, per-IP bucket that no API key can raise.

And it is worse than two minutes when the burst is sustained. After the runs above, the VPS IP was still 429 more than ten minutes later, through a 150 s cooldown and at 1 rps. The same request from a different IP returned 200, and attaching our Jupiter key changed nothing — so the penalty is per-IP and permanent until it decays, not per-account and not liftable.

The same tokens the wallet actually holds, sold to SOL two ways. Raptor's docs claim "free to use with no rate limits"; measured, that claim holds — and preparation is the only phase where a lane difference actually shows, because Jupiter's gate serialises and Raptor's does not.

Twenty concurrent builds in 641 ms with not one rejection is a different regime from a 0.5 rps gate. Raptor's preparation throughput is an order of magnitude above what Jupiter's quota allows — that, not price, is the argument for it.

But the landing half of that trade is still broken. Re-tested with better instrumentation: a Raptor-built tx simulated clean (cu 78,367), /send-transaction returned HTTP 200 + a signature in 190 ms — and then Raptor reported it pending while the chain reported not found on every one of eight polls over 16 seconds. That is now five accepted Raptor sends, none on-chain. The docs explain the likely mechanism: /send-transaction sends via Yellowstone Jet TPU, which is a self-host flag (--enable-yellowstone-jet) — a hosted instance with it off would accept, queue, and never broadcast, which is exactly the shape observed.

So bulk has a real choice, and it is a risk trade, not a price one. Raptor prepares a batch in one parallel round (~0.64 s for 20 concurrent) where Jupiter needs ~2 s per token and then the same again to land each one — but a Raptor tx carries no requestId, so nothing can /execute it: it lands through our own RPC (1.7–5.0 s each measured), with no server-side simulation to catch the transfer-fee class from §"Two things the real run taught us". If bulk throughput matters, the honest lever is the Jupiter quota, not the lane. Use Raptor for bulk preparation only if the sim + chain-verify guards are added first.

One more thing the docs surface that is worth a look before any of this: Raptor also exposes POST /swap (build only) and a WebSocket /stream/swap that streams pre-built transactions and re-sends the latest one after 10 slots without an update. For a basket that is a better shape than N one-shot calls — untested here, and out of scope for this document.

Risks

  • Sampling error is the live risk, and it nearly shipped. A five-pair benchmark implied +131 bps of Raptor edge; a 40-mint random sample gave +5 bps mean / 0 median. Any provider decision from here must carry its n, and the promotion bar is ≥100 priced pairs.
  • Raptor's latency is unstable — 189–656 ms in one run against a 191 ms warm-loop measurement, and it measured 528 ms p50 on fresh mints. It must not sit on a latency-critical path.
  • The keyless bucket is a cliff, not a slope. ~75 rps is fine until it isn't, and then the IP is locked out for ~120 s. Anything that fans out or retries will find that cliff.
  • Route instability. The same pair returned different venues on consecutive attempts, so a simulated "OK" is evidence about that build, not a guarantee about the next one. Simulate the transaction you are about to send, not one you built earlier.
  • Most of the book is untradeable at our size — 28 of 40 random mints were dead or under $5k liquidity — so any routing gain applies to a minority of pairs and can never move the aggregate much.
  • Transfer-fee tokens are a blind spot in the current model. Nothing in the shared candidate shape knows a mint's token-program extensions, so a fee-bearing mint looks like any other until the transaction fails to land.
  • Raptor's send path returned a signature for transactions it did not broadcast. Three Raptor-built sells and one Jupiter-built one all got HTTP 200 + a signature from /send-transaction; none of the four appeared on-chain after 33 s. Any caller that treats "200 + signature" as "submitted" will report a swap that never happened. This is the highest-value thing in this document to explain before trusting that path.
  • A signature is not a landing, anywhere. The only swap in these tests that was proven to execute is the one whose balance moved and whose tx is in the wallet's history. Confirmation must be read from the chain, never from a provider's response body.
  • Bulk is where the lanes differ most, and where the trade is hardest. Raptor prepares five tokens in 644 ms where Jupiter's gate needs ten seconds, and it took 20 concurrent builds with zero rejections — but a Raptor tx cannot be landed by anything (five accepted sends, none on-chain), carries no requestId, and gets no simulation. Moving volume onto it without the simulate and chain-verify guards first means more phantom trades, faster.
  • The Jupiter quota is the real bulk ceiling, and it is not ours to raise from code. The lever is the account plan, not the router. Budgeting at 0.5 rps produced 429s even at exactly 0.5, and this workstream's own experiments drained the shared key twice.
  • swap.io stays an oracle only — no build endpoint exists, it omits Raptor, and it is an undocumented third-party internal API with no SLA. Off by default, behind SWAP_IO_BASE, never on the swap path.

What this means

  • The expensive part of /order is the simulation, and that is worth paying for on the execution path. Raptor and DFlow build a transaction in one call at ~191 ms and ~243 ms; Jupiter's Lite lane builds one in two calls at ~39 ms. What the extra ~170 ms on /order actually buys is the pre-flight simulation — the thing that refused four of our ten batch calls with `Insufficient funds` instead of handing back a transaction that could not land.
  • So the right shape is two lanes, not one fastest lane. The Lite lane is the quote and estimate lane — fastest by 5×, and now proven able to reach a tx on every pair. The keyed /order lane stays the execution lane because it has a quota tied to our account and it validates before it builds. Nothing here argues for moving execution onto the unquota'd lane.
  • No single provider wins on price, which is the strongest argument for keeping the best-of pick. Raptor beats Jupiter's best by +0.55 % on DEW→SOL and +1.31 % on DEW→USDC, then loses by −2.41 % on DEW→BPX. Averages hide this: Raptor is only −0.655 % on average while being both the best and the worst source depending on the pair.
  • The measurement validates wiring this repo already has. Raptor is already a provider in the swap path — that is not luck, and the numbers now say why: it is the only source measured that beats Jupiter anywhere at all.
  • DFlow is the one clear reject, and not only on price. Worst measured quote (−1.04 % average, −1.54 % on DEW→SOL), ~245 ms, and its transactionVersion=v1 output cannot be signed by @solana/web3.js — adopting it would mean adding @solana/kit to sign a slower, worse-priced route.
  • Titan cannot be judged from outside — it needs an API key, so it stays "not evaluable" rather than "rejected". And solana-dex-superagg is not a provider: it is the same best-of idea already implemented in this repo, in Rust.
  • swap.io is genuinely useful and genuinely not an execution path. One keyless call gives a same-moment, multi-provider price read, which is exactly the instrument this analysis needed. But no build/swap endpoint exists on it, it omits Raptor (so its best-of missed the DEW→SOL winner), and a reviewer aggregator should never sit on the critical path.
  • The trap worth carrying forward: 200 OK is not success on /order. Every Jupiter /order host answered 200 with an empty transaction and errorMessage: "Insufficient funds" when the wallet lacked the input token, while the Lite build happily produced a transaction the wallet could not afford. Any caller that checks only response.ok would take an empty transaction and fail downstream instead of here.
  • And the fastest lane is the one with the ceiling we cannot raise. The Lite lane is keyless — a bogus x-api-key still returns 200 — so its per-IP limit is not ours to raise. Under the earlier non-isolated batch it returned 429 on 5/5 calls; isolated, 5/5 clean. It is fast precisely where it is unquota'd, which is another reason it stays off the execution path.

  • src/utils/token-transfer-fee.ts (new). Reads a mint's own transferFeeConfig extension (cached 10 min, tolerates both the flat and nested RPC shapes, picks the config in force for the current epoch) and raises slippage to fee + margin — SWAP_TRANSFER_FEE_MARGIN_BPS, default 30. It never lowers a slippage, and passes the -1 Auto sentinel through untouched so resolveAutoSlippageBps keeps owning it. Fails open: an unreadable mint returns 0 and the swap proceeds exactly as before.
  • prepareSwapTransaction applies the floor once, so every lane below it — order, Lite and the arb/Raptor path — inherits it. No-op for classic SPL mints, which is almost every swap.
  • JupiterSwapQuoteError.venueRefused (new flag). /order reporting errorMessage on a 200 is now distinguishable from a transport fault, because the venue's own reason is the only simulation we have.
  • prepareDeskSwap now rethrows a venue refusal instead of falling back to Lite. A 500 or a 429 still falls back exactly as before — only a decision by the venue aborts.
  • Tests: 18 new across token-transfer-fee.test.ts and jupiter-swap-quote.refusal.test.ts; all 48 pre-existing swap tests still pass, including the one that asserts a 500 does fall back to Lite — which is the behaviour deliberately kept.

What was deliberately not changed

  • The direct and batch architectures. They measured right; a rewrite would be churn.
  • skipPreflight: true on the RPC fallback. Flagged as a guardrail gap, but it is belt-and-braces next to the fee floor, and changing it would add a simulation round trip to every fallback send. Left for a measured decision, not a guess.
  • Raptor's unused send path. Not on the hot path, so removing it is cleanup rather than a fix — and someone may wire it up once the Jet question is answered.
  • The fan-out, the hops escalation, and everything in the "rejected" rows above.
